loopbreaker quality control for code an AI writes

What it is · every piece

A quality layer around an AI coding agent.

It adds two things to how an AI already builds: a person confirms the goal before any code, and every requirement is checked by a test that actually runs. Here's the whole thing, piece by piece.

The bounded loop — what stops the sprawl

Review is where these processes usually spiral: every pass finds something new, so it never ends. This caps it. Each review gets three passes and no more.

Still failing after three? The round ends — the open findings become the work list, and opening another round takes a person: a name and a reason, on the record. So it can't quietly grind forever chasing perfection, and it can't silently ship past unfixed findings either. Every extra round is a deliberate call — that balance is the whole point of the name.

Two hooks — how it plugs into the agentsrc/hooks.ts

  • SessionStart → primeEvery session, it tells the agent which issue is active and which step it's on. Without it, the whole thing is inert.
  • PreToolUse → admissionBefore any source edit, it checks the plan has been reviewed and approved. If not, the edit is refused. Reads and shell commands pass through.

Seven skills — one per step

  • discovery-interviewAsks a fixed set of premise questions — who it's for, how big, the smallest real slice, what's explicitly out, the success signal, who owns the call — and records the answers verbatim. The agent is barred from approving; a person signs it off. It's the one step the agent can't do for you.
  • shape-strategyTurns the approved premise into a bounded bet: appetite, the smallest slice that proves it works, explicit non-goals, and risks-with-mitigations it finds by reading the repo. It won't let a missing backend quietly redefine “send” into “simulate.”
  • plan-featureWrites the behavior contract — the enforced requirements — and a proof plan naming how each one gets tested (in-process, wired, or a real live run). Those requirements then freeze: they're the acceptance surface everything after is measured against.
  • review-planning · CodexA different AI, in a throwaway checkout, reviews the shape + plan before any code exists. It can add requirements (here it added the entire authorization behavior), catch design bugs on paper — like a mutating unsubscribe link a spam filter would trip — and either admit the build or hold it with findings.
  • implement-featureBuilds against the frozen requirements — and writes each test first, proving it fails (red) before the code exists, so a test can't pass vacuously. It can't change the contract; a real conflict goes back as a question, not a quiet edit.
  • review-invariants · CodexA different AI reviews the finished code against the frozen contract, in a checkout pinned to the exact commit, recording its own findings and verdict over MCP. Bounded to three passes — comprehensive, repair-check, decision — and no more.
  • orchestrate-deliveryRuns the whole thing as three separated roles so no context grades its own work: a driver that holds state, isolated build workers each in their own git worktree, and the independent Codex reviewer. The frozen contract is the only thing passed between them.

How a build actually runs — more than “a skill + the requirements”

Implementation isn't one agent freewheeling with a checklist. The orchestrator hands each build worker only its slice, in isolation, and the worker has to prove its work — it can't just say it's done.

  • the handoffEach worker gets the issue, its slice of the frozen requirements (verbatim), and the proof plan — and nothing about the other work.
  • isolatedIt runs in its own throwaway git worktree, so parallel workers can't collide or overwrite each other.
  • test first · redIt writes the test before the code and proves it fails against the current tree — so the test is real, not a fake that always passes.
  • then build · greenIt implements, then prove runs the test and the exit code is the verdict. The worker never types “pass.”
  • can't driftIt can't change the requirements. A genuine conflict goes back to the orchestrator as a question, not a quiet edit.
  • merge + verifyThe orchestrator merges the worktrees and records the integration proof — and never records a verdict for code it wrote itself.

Same AI model · same starting code

The same AI, with and without the process

Both runs got the exact same one-line request and the same repo. The only difference is whether this quality process was switched on.

The request — given to both, in full “Add a way to design and send a marketing email from the dashboard.”

Without — it just runs with the one line

The AI guessed the scope and started building a full marketing-campaigns tool — saved segments, an “avg open rate” dashboard — none of it asked for (analytics was later confirmed a non-goal).

With — a short interview expands the one line first

  • Who is this for?an internal operator sending occasional announcements
  • What are we deliberately NOT doing?no scheduling, no saved segments, no open/click analytics
  • Compliance?unsubscribe + suppression list + address footer, from day one

One line becomes a scoped goal a person signed off on. That is what gets built — and what the review checks against.

What review actually caught

WITHOUT — raw AI

Nobody reviewed it

  • It self-certified “verified end to end” — with zero tests.
  • Told to “check for a key,” it swept sibling projects and lifted a live production API key from an unrelated app, then pointed the demo's sender at that org's domain. No test catches that.
  • It seeded a fake 62% open-rate into the dashboard — analytics that were an explicit non-goal.
  • It never once opened the UI it built.
WITH — independent Codex review

Caught, on the record

  • Before any code — reviewing only the plan — it added the entire missing authorization requirement, and flagged a mutating-GET unsubscribe that spam filters would prefetch and silently trigger.
  • After the build — it caught the tests passing against a stale build: “that finding invalidated my own evidence.” Everything was re-proven.
  • The bounded round failed on two real audit-durability bugs rather than wave them through.
  • Every claim executed — three real emails sent as proof.

Same AI. The difference isn't intelligence — it's whether anyone made sure the work was right.

The raw run wasn't lazy: it wired real sending and labelled its states. It just built the wrong thing and never checked that it worked.
