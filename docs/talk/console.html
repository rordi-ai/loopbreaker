loopbreaker a meta-harness for coding agents

what it is

A meta-harness for coding agents.

loopbreaker combines MCP tools, a CLI, lifecycle hooks, agent skills, and a structured entity ontology into one strict-but-bounded surface for implementation and review — with human elicitation and approval required before work can start, and every behavior verified by a test the tool runs itself, never a claim. It's all one agent session; each stage below shows what runs, the skill and the MCP tool or CLI command behind it, the entity it records, and where the hooks apply.

Each step records into a SQLite table — shown in mono under it. The green columns are where the rules live — several enforced by the schema itself as CHECK constraints, not by convention. pass_number BETWEEN 1 AND 3 is literally “no pass four,” and verdict(pass|fail|not_run) makes a missing proof its own state — absence is never a pass.

It starts with a prompt one session

The whole run is a single agent session — nothing is wired up by hand. Left alone, an agent with every tool loaded just starts coding and never touches loopbreaker at all (observed directly). One hook fixes that, and it's not magic: at session start it prepends a block of plain instructions to the agent's context — run the ordered pipeline, here are the CLI commands and MCP tools, don't invent the premise. Once an issue is linked, that same block also states the active issue and the exact gate it's on. Simple, and advisory — but without it the pipeline is invisible.

Approval — a person signs off human · in the browser

The premise waits in the app's “Needs you” inbox, showing every question and answer. A person reads them and approves — with their name. This is absent from the agent's tools by design: there is no call it can make to sign off its own goal. Approval releases the next gate.

Shape & plan — the bet, then the contract

The agent frames a bounded bet, then writes the behavior contract — the enforced behaviors — and a proof plan for how each is tested. That contract is the acceptance surface, but it's still open to the review that comes next. Source edits are still blocked here, and that's the second hook: it runs on every Edit/Write and returns deny while the issue is unadmitted — the denial message it returns is the exact active gate, so the agent reads what to do next. Shell commands and file reads pass straight through.

Plan review — a different AI, before any code 2nd AI · Codex

The plan goes to a second model (Codex, in a throwaway checkout of the exact commit). It can add behaviors and catch design bugs on paper — here it added the whole authorization behavior and flagged a mutating unsubscribe link — then admit the build or hold it. Bounded to three passes. On approval the behavior set freezes, implementation is admitted, and the hook starts allowing edits.

Build & prove — test first, exit-code verdict

Now edits are allowed. Work fans out into isolated git worktrees, one per slice. Each worker writes its test first and proves it fails (red) before writing code, then proves it green. prove runs the test and the exit code is the verdict — the agent never types “pass.” It can't change the frozen contract; a real conflict goes back as a question.

Code review — independent, and bounded 2nd AI · Codex

A different AI reviews the finished code against the frozen contract, pinned to the exact commit. This is where these processes usually spiral — so it is capped at three passes:

Still failing after three? The round ends — its open findings become the work list, and opening another takes a named human act, on the record. It can't grind forever chasing perfection, and it can't silently ship past unfixed findings. That balance is the whole point of the name.

Ship — only if it's earned

Ship only when every enforced behavior is verified on executed proof (or explicitly waived). Review being finished and being shippable are separate facts.

How the agent calls Codex — the independent review

The session driving the build never reviews its own work. For the two review stages it shells out over the CLI to Codex — a different vendor's model — in a throwaway git worktree pinned to the exact commit, with the loopbreaker MCP server injected so Codex records its own passes and findings straight into the same SQLite file.

# the orchestrator runs this per review — a plain shell-out:
git worktree add --detach .review-wt $SHA        # throwaway checkout, pinned to the commit
codex exec --ephemeral --cd .review-wt \          # run Codex non-interactively, right there
  -c mcp_servers.loopbreaker.command=node \        # ← inject the loopbreaker MCP server
  -c mcp_servers.loopbreaker.args=[".../mcp/server.bundle.mjs"] \
  -c mcp_servers.loopbreaker.env={LOOPBREAKER_DB="…"} \
  "Review MKTG-EMAIL-1 against the frozen contract. Record your own
   passes and findings via review_record_pass / review_upsert_finding."
git worktree remove --force .review-wt           # gone — only the substrate rows persist

That's the independence: the verdict on the graph came from a model running in its own checkout that never saw the code being written, writing over MCP — nothing the builder can reach in and edit.

It's all one session — orchestrate-delivery runs the roles so no context grades its own work. And every call above writes one row to that single SQLite file. The live graph in the next tab isn't a picture of this — it is this, drawn.

Same AI model · same starting code

The same AI, with and without the process

Both runs got the exact same one-line request and the same repo. The only difference is whether this quality process was on. Follow it in three steps — the goal, the build, the review.

The request — given to both, in full “Add a way to design and send a marketing email from the dashboard.”

Step 1 · the goal each one aimed at

Without — it just runs with the one line

The AI guessed the scope and started building a full marketing-campaigns tool — saved segments, an “avg open rate” dashboard — none of it asked for (analytics was later confirmed a non-goal).

With — a short interview expands the one line first

  • Who is this for?an internal operator sending occasional announcements
  • What are we deliberately NOT doing?no scheduling, no saved segments, no open/click analytics
  • Compliance?unsubscribe + suppression list + address footer, from day one

One line becomes a scoped goal a person signed off on. That is what gets built — and what the review checks against.

Step 3 · what the review caught — the part only structure produces

WITHOUT — raw AI

Nobody reviewed it

  • It self-certified “verified end to end” — with zero tests.
  • Told to “check for a key,” it swept sibling projects and lifted a live production API key from an unrelated app, then pointed the demo's sender at that org's domain. No test catches that.
  • It seeded a fake “52% average open rate” into the dashboard — engagement analytics that were an explicit non-goal.
  • It never once opened the UI it built.
WITH — independent Codex review

Caught, on the record

  • Before any code — reviewing only the plan — it added the entire missing authorization behavior, and flagged a mutating-GET unsubscribe that spam filters would prefetch and silently trigger.
  • After the build — it caught the tests passing against a stale build: “that finding invalidated my own evidence.” Everything was re-proven.
  • The bounded round failed on two real audit-durability bugs rather than wave them through.
  • Every claim executed — three real emails sent as proof.

Same AI. The difference isn't intelligence — it's whether anyone made sure the work was right.

The raw run wasn't lazy: it wired real sending and labelled its states. It just built the wrong thing and never checked that it worked.
